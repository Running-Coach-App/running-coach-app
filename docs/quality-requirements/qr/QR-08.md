# QR-08: Let A Stranger Prove The Product Sends Nothing

Anyone who has the repository can run one command from a clean checkout and see for themselves that the product cannot send a runner's data anywhere, and that nothing it ships carries a known vulnerability.

- **Status:** Active
- **Characteristic:** Security
- **Sub-characteristic:** Confidentiality
- **Business importance:** High
- **Technical risk:** Low

This requirement is the `Customer`'s, in his own words. In [the Week 5 meeting](https://github.com/Running-Coach-App/running-coach-app/blob/main/reports/week-05/meeting-transcript.md) he asked for "some kind of automated scanner in the repository that checks for vulnerabilities, security problems, and package dependencies", said "that is a quality requirement from me", and gave the reason: "The most important qualities are security and proof, for open source, that you are not sending data somewhere. People know the scanner: they can run it and see." He repeated the two halves at the end of that meeting: "Google quality requirements for publishing in Play Store, and a security check in the repository that I can run for myself, and that anyone who wants to install can run."

The second half is what makes this a requirement about the repository rather than about the app. A claim that the product keeps a runner's data on the phone is worth nothing if believing it means trusting the team. The point is that it does not: the reader runs the check.

It also carries Google's `SDK_Maintenance` criterion, which states that a developer is "accountable for the entire app codebase, inclusive of any third-party SDKs used". [`docs/research/play-store-quality.md`](../../research/play-store-quality.md) carries the research behind both halves.

## Scenario

### Source

Somebody outside the team who is deciding whether to install the product — the `Customer`, a reviewer, or a runner who found the repository.

### Stimulus

They clone the repository and want to know, without reading all of it and without trusting its authors, whether the app can send their run anywhere and whether it ships anything known to be vulnerable.

### Environment

A clean checkout on Linux or macOS, with `bash`, `curl`, and `python3`. No Android SDK, no Gradle, no Java, and no account anywhere.

### Artifact

`scripts/scan.sh`, the manifest, `app/gradle.lockfile`, and the tracked files of the repository.

### Response

One command shall answer all three questions and shall say which it could not answer. It shall fail loudly rather than pass quietly: a check that cannot run shall stop the scan with a distinct exit code, and shall never be reported as a pass.

### Response Measure

`./scripts/scan.sh` exits `0` when, and only when: no dependency on `releaseRuntimeClasspath` has an advisory in OSV.dev; the main manifest declares none of `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`, `CHANGE_NETWORK_STATE`, `CHANGE_WIFI_STATE`, or `NEARBY_WIFI_DEVICES`; no file under `app/src/main` references a networking type; a built release APK, if one is present, declares no network permission either; no tracked file matches a private key, token, or API key pattern; and `local.properties` is untracked. It exits `1` when a check fails and `2` when a check could not run. Adding `android.permission.INTERNET` to the main manifest makes it exit `1`. Campus upload for [`DEC-031`](../../decisions.md#dec-031) lives in the debug source set only.

Build-time dependencies with advisories are reported as warnings and do not fail the scan. They are not in the APK and cannot reach a runner; the script says so where it prints them, and the research page gives the reasoning and the issue tracking the fix.

The advisories can come from either of two sources — `osv-scanner` when it is installed, or the OSV.dev HTTP API when it is not — and the two shall not be able to reach different verdicts. Neither decides anything: each only produces a list of package coordinates and advisory identifiers, and a single classifier decides what fails. An advisory against a package that is not in the lockfile at all shall count as shipping, because it cannot be shown not to. If a source reports findings and none can be parsed from its output, the scan shall stop with its own exit code rather than report a pass.

## QRT-01

The scan is run from a clean checkout, and then run again against a deliberately broken manifest to prove it still fails.

- **Status:** Active
- **Level:** `scripted`
- **Runs at:** a development machine and the `Security scan` workflow on every pull request and every push to `main`, as `./scripts/scan.sh`.

The level is `scripted` rather than `deployed` for the reason every test in this repository is: there is no deployment. It needs no Android toolchain by design, since a stranger who has to install the Android SDK before they can check a privacy claim will not check it.

### Procedure

1. From a clean checkout, run `./scripts/scan.sh` and record its output and exit code.
2. Add `<uses-permission android:name="android.permission.INTERNET" />` to `app/src/main/AndroidManifest.xml`.
3. Run `./scripts/scan.sh` again and record that it fails, and that it names the permission.
4. Restore the manifest with `git checkout -- app/src/main/AndroidManifest.xml`.
5. Confirm the `Security scan` workflow runs both steps, so the test cannot rot into a check that always passes.

**Pass when:** step 1 exits `0` with every check reported as a pass, step 3 exits `1` and prints `the manifest declares a network permission`, and the workflow performs both.
