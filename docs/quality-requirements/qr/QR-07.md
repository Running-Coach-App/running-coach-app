# QR-07: Power Location Only While A Session Runs

The product keeps the phone's location powered for exactly as long as a session is running, and releases it the moment the session stops.

- **Status:** Active
- **Characteristic:** Performance Efficiency
- **Sub-characteristic:** Resource Utilisation
- **Business importance:** Medium
- **Technical risk:** Medium

This is Google's `Background_Service_Optimization` criterion, which reads "App avoids running unnecessarily long services in the background to ensure the smooth running of the user's device" and names, among its examples of poor use, **keeping GPS powered on**. [`docs/research/play-store-quality.md`](../../research/play-store-quality.md) carries the research, and it is the criterion this product is closest to failing by design: a coach that does not know where the runner is cannot speak pace or distance.

The defensible line is not that the product avoids GPS but that it holds it only while coaching. A running coach that keeps a fix for the twenty-three hours a day nobody is running is the drain Google is describing; one that holds it for a forty-minute run is doing the job the runner asked for.

The `Customer` put it as "Play Store will punish an app that takes a lot of CPU or battery". The research found that the battery vital Play actually enforces is excessive partial wake locks, which Google lists as in beta and not yet affecting discoverability, so the pressure here is real but currently soft. That is why this is `Medium` business importance and [`QR-06`](QR-06.md) is `High`.

## Scenario

### Source

A runner who finishes a run and puts the phone away, and the Android system's own power management.

### Stimulus

A session is started, run for some minutes, and stopped — and then the phone is left alone for a long time. Separately, the app is killed by the system while a session is running.

### Environment

A phone at `minSdk` 26 or above, with location permission granted, and no other app requesting location.

### Artifact

The location updates `CoachService` requests from `LocationManager`, and the foreground service that holds them.

### Response

The product shall request location updates when a session starts and shall remove them when the session stops, when the service is destroyed, and when the system kills the process. After a session stops, the product shall hold no location request at all.

### Response Measure

With a session stopped, the system reports no location request belonging to `app.runningcoach`. With a session running, it reports exactly one. The transition happens within one second of the stop, not at some later cleanup.

## QRT-01

The system's own record of who is asking for location is read before, during, and after a session.

- **Status:** Active
- **Level:** `manual`
- **Runs at:** a physical Android phone connected over `adb`, against the debug APK attached to the current release.

The level is `manual` because this cannot be observed from the JVM: the request lives in `LocationManager`, an Android service, and the only honest witness is the platform's own accounting. It is not `scripted` because asserting that `removeUpdates` appears in the source would test the text of the code rather than the behaviour of the phone, which is the mistake this requirement exists to avoid.

### Procedure

1. Install the debug APK on a phone and grant location permission.
2. With no session running, read the baseline:
   `adb shell dumpsys location | grep -i -A2 'app.runningcoach'`
   Record that no location request is listed.
3. Start a session in the app. Read the same command again and record the one request that now appears, with the interval it names.
4. Let the session run for at least three minutes, then stop it from the notification.
5. Within one second of the stop, read the same command a third time.
6. Force-stop the app (`adb shell am force-stop app.runningcoach`) during a fourth, separate session, and read the command once more.

**Pass when:** step 2 shows no request, step 3 shows exactly one, step 5 shows none, and step 6 shows none. Paste the three `dumpsys` extracts into the evidence file as the record.

**Not verified as of `SPRINT-07`.** The test is defined and has not been run: it needs a physical phone, and the `Customer` has not installed the product, so the only phone available is a team member's. The testing plan carries the `Not verified` status rather than a pass nobody observed.
