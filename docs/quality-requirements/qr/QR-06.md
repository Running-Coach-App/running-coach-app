# QR-06: Finish A Session Without Crashing Or Going Unresponsive

A session runs from start to stop without the app crashing or stopping responding, whatever the phone's location provider reports.

- **Status:** Active
- **Characteristic:** Reliability
- **Sub-characteristic:** Faultlessness
- **Business importance:** High
- **Technical risk:** Medium

This is Google's `Stability_ANR` criterion, the one core app quality criterion with a published number under it. [`docs/research/play-store-quality.md`](../../research/play-store-quality.md) carries the research. Exceeding **1.09%** user-perceived crash rate or **0.47%** user-perceived ANR rate across devices makes an app "likely to be less discoverable on Google Play", and the per-phone-model threshold for each is **8%**, which is the `Customer`'s "if it crashes a lot on some phones they will hide it from Google Play for those phones".

Those are rates over daily active users across 28 days. This product has none, because nobody outside the team has installed it and [`TOS-02`](../../threshold-of-success.md#tos-02) is recorded as missed. The requirement is therefore written against what one phone and one test can show, and the store rate becomes checkable once there are runners.

## Scenario

### Source

A runner using the coach for a whole run, and the phone's location provider feeding it.

### Stimulus

A session of up to an hour, during which the location fix comes and goes, the reported position jumps, and the runner asks spoken questions throughout.

### Environment

A session running in the foreground service with the screen off, on a phone at `minSdk` 26 or above, with no network available.

### Artifact

The coach's decision loop in `SessionEngine`, driven once a second by `CoachService` on the main thread.

### Response

The session shall run to its stop. No input the location provider can produce shall raise an unhandled exception, and no single pass of the decision loop shall hold the main thread long enough for the system to raise an "input dispatching timed out" error.

### Response Measure

Across a simulated session of 60 minutes at the real one-second cadence, with the fix dropping for 90 seconds in every 10 minutes, every pass of the loop completes, no exception is raised, at least one line is spoken, and the whole session's loop time stays under 2 seconds in total — against the 16 milliseconds one frame allows for a single pass. State kept for the screen stays bounded across 500 spoken answers, and 50 start-and-stop cycles leave no elapsed time behind.

Once the product has runners, the measure gains the store's own: user-perceived crash rate under 1.09% and user-perceived ANR rate under 0.47% over 28 days, read from Android vitals.

## QRT-01

An hour-long session is driven through the coach's decision loop with the inputs a real run produces.

- **Status:** Active
- **Level:** `scripted`
- **Runs at:** the JVM unit suite on a development machine and in the Android build workflow, as `gradle :app:testDebugUnitTest --tests '*StabilitySoakTest*'`.

The level is `scripted` and not `deployed` because there is no deployment: the product is an Android application and the team has no device farm. It is not `manual` because the loop is pure Kotlin with no Android types, so it can be driven directly, which is the arrangement [`QR-02`](QR-02.md) already relies on.

### Procedure

1. From a clean checkout with JDK 17, run `gradle :app:testDebugUnitTest --tests '*StabilitySoakTest*'`.
2. `anHourLongSessionNeitherThrowsNorStopsSpeaking` drives 3,600 one-second ticks with the fix dropping for 90 seconds in every 10 minutes, then stops the session.
3. `theDecisionLoopStaysWellInsideAFrameBudgetAcrossAWholeSession` times the same number of ticks and compares the total against the budget.
4. `aSessionSurvivesTicksThatGoBackwardsRepeatOrJump` feeds ticks that go backwards, repeat, and jump a thousand kilometres, which is what [`DEC-032`](../../decisions.md#dec-032) says to pass through rather than correct.
5. `answeringRepeatedlyThroughoutASessionNeitherThrowsNorGrowsWithoutBound` asks 500 questions and checks the retained lines stay bounded.
6. `aSessionCanBeStartedAndStoppedRepeatedlyWithoutLeavingStateBehind` runs 50 cycles and checks the next session starts clean.

**Pass when:** all five tests pass, no test throws, and the timed test stays under its budget.

The store's own rates stay in the response measure above rather than becoming a `QRT-02`. A test that needs a published app with enough daily active users for Play to compute a 28-day rate cannot be scheduled into any sprint that is left, and a permanently unverifiable row in the testing plan says less than this sentence does. Publishing needs the signed App Bundle [`#137`](https://github.com/Running-Coach-App/running-coach-app/issues/137) and a store listing; [`docs/research/play-store-quality.md`](../../research/play-store-quality.md) lists what would have to change.
