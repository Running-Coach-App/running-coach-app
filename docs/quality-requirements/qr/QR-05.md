# QR-05: Diagnose A Failed Coaching Line From Its Record

An operator can diagnose a failed or delayed coaching line from the telemetry record without asking the runner to reproduce the run.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

The system operator responsible for explaining a report that the coach went quiet or spoke late.

### Stimulus

A spoken line is delayed or cannot be spoken during a session, and the operator needs to find what happened to that line.

### Environment

The app has recorded the session's telemetry in its local JSONL file, which the runner can export. There is no staging deployment in the project. The test therefore exercises the file sink with a scripted failed line and declares the deviation from a deployed test.

### Artifact

The per-line record in `events.jsonl`, as defined by [`FR-014`](../../functional-requirements/fr/FR-014.md) and [`SLI-01`](../../observability.md#sli-01).

### Response

The operator finds the record by its `line_id` and can identify its session, kind, outcome, occurrence time, and delay without asking the runner to reproduce the run.

### Response Measure

For a scripted failed stats line, exactly one record is found by its `line_id`. The record has the expected `session_id`, `line_kind`, `outcome`, `occurred_at`, and `latency_ms`, and contains no field that identifies the runner.

## QRT-01

An operator can diagnose a failed line from its stored telemetry record.

- **Status:** Active
- **Level:** `scripted`
- **Runs at:** a scripted check of the SLI-01 per-line record, using `gradle :app:testDebugUnitTest --tests '*TelemetryTest.aFailedLineCanBeDiagnosedByIdFromTheStoredTelemetry'` on a development machine.

### Procedure

1. From a clean checkout with JDK 17, run the command above.
2. The test writes a scripted `dropped_unavailable` stats line through the production `FileTelemetrySink` into a temporary `events.jsonl` file.
3. The test reads the file by `line_id` and compares the full record with the expected diagnostic fields.

**Pass when:** the test finds exactly one record for the scripted `line_id`, all fields match the expected session, line kind, outcome, time, and delay, and no runner identity is present.

**Deviation:** the assignment calls for a deployed run. The team has no staging environment, so this check runs scripted against the production file sink in a unit test. It verifies that the stored record is diagnosable, but does not claim to verify a deployed instance.
