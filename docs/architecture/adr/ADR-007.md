# ADR-007: Measure Distance Only From Fixes The Product Can Check

- **Status:** Accepted
- **Created:** 2026-11-20
- **Updated:** 2026-11-20
- **Containers:** `coach app`
- **Addresses:** [`FR-002`](../../functional-requirements/fr/FR-002.md), [`FR-006`](../../functional-requirements/fr/FR-006.md), [`QR-04`](../../quality-requirements/qr/QR-04.md)

## Context

The product spoke whatever the location provider gave it. `listenForLocation()` asked for every fix the provider could produce, once a second, with a minimum displacement of `0f`, and `onLocationChanged()` added the difference between consecutive fixes to the session's distance without a single test on the way.

A GPS fix wanders while the phone does not move, by metres outdoors and by tens of metres indoors, and `Location.distanceTo` is never negative, so that wander only ever accumulated. [Issue #251](https://github.com/Running-Coach-App/running-coach-app/issues/251) is the measurement: a phone lying still on a desk for four and a half minutes recorded **516 m**, and at 33 seconds the lock screen read `0:33  1:38 /km  0.3 km`, which is about 33 kilometres per hour.

Three forces make this a decision rather than a preference:

- **[`FR-002`](../../functional-requirements/fr/FR-002.md) requires the pace and the distance to be spoken** every cadence. It does not say they may be wrong, and [`FR-006`](../../functional-requirements/fr/FR-006.md) already gives the product a way to say that a stat is not available, so refusing to state a number costs no new vocabulary.
- **[`QR-04`](../../quality-requirements/qr/QR-04.md) covers a fix that is lost.** This is the opposite case: a fix that is present, delivered, and wrong. Nothing in the product distinguished a good fix from a bad one, and `Location.getAccuracy()` was never read anywhere in the product.
- **The phone knows more than its coordinates.** A fix carries an accuracy radius and, on a real GPS fix, a Doppler-derived speed that does not drift with the position wander. Both were being thrown away.

What this affects is not only spoken. `distance_m` on `session_stopped`, the History screen, the `Customer`'s export for [#223](https://github.com/Running-Coach-App/running-coach-app/issues/223), and every `UT-01` participant's session carry whatever this arithmetic produced.

## Considered Options

- **Keep trusting every fix, and smooth the result afterwards.** A moving average or a Kalman filter over the accumulated distance would hide the jitter in a long run. It loses because smoothing a number that is wrong in one direction only cannot recover the right one: a stationary phone's 516 m smooths to a confident 516 m. It also puts the arithmetic further from the fix that caused it, where no unit test can state the case it is meant to handle.
- **Ask the platform to filter, with a minimum displacement in `requestLocationUpdates`.** Passing a minimum distance instead of `0f` moves the test into Android. It loses because the platform's displacement test compares the same wandering coordinates, so it cannot tell a wander from a step either, and because it moves the rule into a call a unit test cannot reach, which is the mistake [`ADR-003`](ADR-003.md) exists to avoid.
- **Use the phone's step counter or activity recognition to decide whether the runner is moving.** Both are better evidence of running than any position difference. They lose for this release because activity recognition needs a runtime permission the product does not hold and [`QR-08`](../../quality-requirements/qr/QR-08.md) is the promise that the shipped build asks for as little as possible, and because neither is reachable from a unit test without a device.
- **Test each fix and each step against what a runner can be, in the product's own code.**

## Decision Outcome

**Test each fix and each step against what a runner can be, in the product's own code.** The rules live in `DistanceFilter`, which holds no Android types, so each case below is a unit test rather than a claim. It beats the other three because it rejects the wander where it enters, keeps every threshold where a reviewer can read it, and needs no permission the shipped build does not already hold.

A fix is measured with only when it reports an accuracy radius no worse than the limit. A step between two such fixes counts only when the provider's own speed does not contradict it, when it is above the noise floor, and when it implies a speed a runner could reach. A pace is spoken only when the average it implies is one a runner could hold.

| Threshold | Value | Why this value |
| --- | --- | --- |
| Accuracy limit | **20 m** | Android reports accuracy as the radius the true position lies within with 68% confidence. At 20 m, two fixes a second apart can differ by tens of metres from noise alone, so a worse fix cannot support a distance claim. It is also well outside a normal outdoor fix, which is 3 m to 10 m, so it does not reject a real run. A fix reporting no accuracy at all is not measured with, because nothing bounds its error. |
| Moving speed | **0.5 m/s** | Slower than a stroll. Below it the provider's own speed says the device is not moving, and that speed is Doppler-derived rather than differenced from the coordinates, so it does not drift with them. This is the rule that stops the desk case. |
| Step speed limit | **12.5 m/s** | The 100 m world record averages about 10.4 m/s and peaks near 12.4 m/s, so no runner exceeds this over a one-second step. A step above it is the fix jumping, not a person running. |
| Average speed limit | **8.0 m/s** | The spoken pace is an average over the whole session, and the 1 km world record is 2:11 per kilometre, or 7.6 m/s. An average above 8 m/s is beyond any human record over any session length, so the product says the pace is not available rather than stating it. |
| Noise floor | **1 m** | Below the resolution of a consumer fix, and cheap to exclude. |

## Consequences

**A fix the product cannot measure with is treated as no fix.** It does not update the staleness clock, so [`QR-04`](../../quality-requirements/qr/QR-04.md)'s handling takes over after its grace period: `location_fix_lost` is recorded, and [`FR-006`](../../functional-requirements/fr/FR-006.md) says once that the pace and the distance are not available. A session run entirely indoors will therefore report a lost fix where it used to report a confident, wrong distance. That is the intended trade, and it will make [the location fix availability metric](../../analytics.md#location-fix-availability) lower and more honest at the same time.

**The product can now under-report distance**, where before it could only over-report it. A runner the provider reckons is moving slower than 0.5 m/s covers no counted distance, and a genuinely poor fix contributes none. [`FR-002`](../../functional-requirements/fr/FR-002.md) is better served by a distance that is too small than by one that cannot be true, but the size of the shortfall is unknown until the moving check on a device in [#251](https://github.com/Running-Coach-App/running-coach-app/issues/251) is done.

**Distance is still the sum of straight lines.** Nothing here makes the total right; it stops the product counting what did not happen. A run around a corner is still measured as a chord, and the error from a one-second cadence is unchanged.

**A fix with no speed is judged on its step alone.** Some providers, and every mock location, may report none, so the rule that stops the desk case cannot apply there. A scripted mock-location run is therefore not evidence that this filtering works, and the check in [#251](https://github.com/Running-Coach-App/running-coach-app/issues/251) has to be a real phone, still and then moving.

**The thresholds are claims about runners, not about this product**, so they do not change when the product does. If one is found wrong it is changed here and in `DistanceFilter` in the same change, and `DistanceFilterTest` asserts all five values so the two cannot drift apart silently.
