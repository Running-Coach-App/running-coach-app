# ADR-003: Keep The Session Logic In A Pure Kotlin Engine

- **Status:** Accepted
- **Created:** 2026-10-22
- **Updated:** 2026-10-22
- **Containers:** `coach app`
- **Addresses:** [`QR-01`](../../quality-requirements/qr/QR-01.md), [`QR-02`](../../quality-requirements/qr/QR-02.md), [`FR-002`](../../functional-requirements/fr/FR-002.md), [`FR-003`](../../functional-requirements/fr/FR-003.md), [`FR-006`](../../functional-requirements/fr/FR-006.md)

## Context

Most of what the customer judges this product on is a decision about what to say and when: which line falls due, whether the effort changed, and what to do when a stat is missing. [`FR-002`](../../functional-requirements/fr/FR-002.md), [`FR-003`](../../functional-requirements/fr/FR-003.md), and [`FR-006`](../../functional-requirements/fr/FR-006.md) are all of that kind, and each one is a rule about timing and wording rather than about Android.

[`QR-02`](../../quality-requirements/qr/QR-02.md) requires those decisions to be checkable from a clean checkout with no device attached, and the course is graded partly on that. Android types make this hard: a class that touches `Service`, `TextToSpeech`, or `LocationManager` needs an emulator or a mocking framework to exercise at all.

## Considered Options

- **Keep the logic in the foreground service.** Fewest files, and the state sits where the sensors arrive. It loses because the service cannot be constructed off a device, so every timing rule would need an instrumented test and the clean-checkout run in [`QR-02`](../../quality-requirements/qr/QR-02.md) would be impossible.
- **Keep the logic in the service and test it through a mocking framework.** It would let the checks run on a developer machine. It loses because the tests would then assert against the mocks rather than against the spoken lines, and the setup cost lands on every new rule.
- **A pure Kotlin engine the service drives.**

## Decision Outcome

A pure Kotlin engine the service drives, in `app/src/main/java/app/runningcoach/SessionEngine.kt`, holding no Android types.

The service feeds it the elapsed time and the distance and plays back the lines it returns, so every rule about what is said and when is decided in a class that a plain JVM test can construct. It beats the other two because the check it enables is the one the quality requirement names, and because the boundary it draws is the same one the requirements already draw: the engine owns the wording and the timing, and the service owns the sensors and the speaking.

## Consequences

The spoken decisions can be exercised without a phone, which is what makes [`QR-02`](../../quality-requirements/qr/QR-02.md) achievable, and a broken rule shows up in a unit test rather than on a run.

The split costs a translation layer. Every value the engine needs has to be handed to it by the service, so a rule that needs a new input means a change in both files, and an engine that is correct is still no proof that the service wires it up correctly. What the service does with sensors and speech stays outside the unit checks, and `docs/setup.md` is where a member confirms it by hand on a device.

The decision accepts these quality attributes:

- **Testability**, covered by [`QR-02`](../../quality-requirements/qr/QR-02.md): the engine is constructible in a plain JVM test, which is what the requirement measures.
- **Time behaviour**, covered by [`QR-01`](../../quality-requirements/qr/QR-01.md): the engine decides a line from values it already holds, adding no input of its own between the due moment and the speaking.
