# ADR-001: Run The Product As One Android Application

- **Status:** Accepted
- **Created:** 2026-10-22
- **Updated:** 2026-10-22
- **Containers:** `coach app`
- **Addresses:** [`FR-001`](../../functional-requirements/fr/FR-001.md), [`FR-002`](../../functional-requirements/fr/FR-002.md), [`FR-006`](../../functional-requirements/fr/FR-006.md), [`QR-01`](../../quality-requirements/qr/QR-01.md), [`QR-03`](../../quality-requirements/qr/QR-03.md), [`QR-04`](../../quality-requirements/qr/QR-04.md)
- **Decision:** [`DEC-006`](../../decisions.md#dec-006), [`DEC-009`](../../decisions.md#dec-009)

## Context

The product has to talk to a runner while the phone is in a pocket, from the phone's own sensors, with nothing sent to a server. [`CON-01`](../../product-vision.md#con-01) fixes Android for the first release, [`CON-03`](../../product-vision.md#con-03) keeps the run on the phone wherever that is possible, and [`CON-04`](../../product-vision.md#con-04) makes the phone's own sensors the baseline input.

That leaves the question of what the product runs as. Everything the coach needs during a session is already on the device: the clock, the location receiver, the microphone, and a voice. Nothing in [the functional requirements](../../functional-requirements/README.md) reads or writes state that outlives a session, so there is no store to keep and no account to hold.

## Considered Options

- **A phone application with a backend service and a database.** A server could hold session history and run a larger model. It loses because no requirement needs state after the session ends, because a round trip contradicts [`DEC-004`](../../decisions.md#dec-004), and because a runner out of signal would lose the coach.
- **A phone application with a local database.** A store on the device would keep past runs. It loses because no requirement in this release reads a past run, and an unused store is a container the team would have to maintain and back up.
- **One Android application, holding the session in memory.**

## Decision Outcome

One Android application, holding the session in memory. It is the only container the product runs as, and it is the only one the container view shows.

It beats the other two because it is the smallest thing that satisfies every functional requirement in this release: the session lives for the length of the run, and every input it needs is on the phone already. It keeps the product usable with no signal, which neither of the server options does, and it removes an entire class of work the team has no weeks for.

Splitting the application into a user interface container and a session container was rejected as well. The screen and the foreground session ship in one package, are installed together, and cannot run on different machines, so they are components inside this container rather than containers of their own.

## Consequences

The product works offline and starts without an account, which is what makes [`QR-03`](../../quality-requirements/qr/QR-03.md) reachable at all.

Nothing survives the session. A runner who stops a session loses it, and a history feature later needs a store, which is a new container and a record that names it.

The decision accepts these quality attributes:

- **Time behaviour**, covered by [`QR-01`](../../quality-requirements/qr/QR-01.md): with no network in the path, the only thing between a due stats line and the speaker is the device itself.
- **Fault tolerance**, covered by [`QR-04`](../../quality-requirements/qr/QR-04.md): the application owns the whole session, so a lost location fix is a missing value rather than a failed call, and the session can keep going.
- **Operability**, covered by [`QR-03`](../../quality-requirements/qr/QR-03.md): one application owns both the controls and the speech, so a control the runner cannot see still reaches the part that talks.
