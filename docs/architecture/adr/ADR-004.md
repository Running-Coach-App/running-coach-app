# ADR-004: Match A Spoken Question On The Phone, With Keywords As The Fallback

- **Status:** Accepted
- **Created:** 2026-10-22
- **Updated:** 2026-10-22
- **Containers:** `coach app`
- **Addresses:** [`FR-004`](../../functional-requirements/fr/FR-004.md), [`FR-005`](../../functional-requirements/fr/FR-005.md), [`QR-01`](../../quality-requirements/qr/QR-01.md), [`QR-03`](../../quality-requirements/qr/QR-03.md)
- **Decision:** [`DEC-008`](../../decisions.md#dec-008), [`DEC-016`](../../decisions.md#dec-016)

## Context

[`FR-004`](../../functional-requirements/fr/FR-004.md) requires the coach to answer a spoken question about the current run without the runner learning a fixed list of commands, and [`FR-005`](../../functional-requirements/fr/FR-005.md) requires an off-topic question to get a short reply that turns the runner back to the run. The `Customer` said in [`DEC-016`](../../decisions.md#dec-016) that there are too many ways to ask for the same stat for a brittle keyword list on its own, and named a small on-device model as the thing to try first.

The answers themselves are narrow: three stats from a session the application already holds. What is open is how a spoken sentence becomes a request for one or more of those stats, and the two parts of that question come apart. Turning speech into text is the platform's job; deciding what the text asks for is the product's.

[`ASM-09`](../../assumptions.md#asm-09) records that whether a small on-device model fits in the remaining weeks is still unmeasured, so the decision has to stand whether or not it does.

## Considered Options

- **A cloud language model.** It would read any wording. It loses because it contradicts [`DEC-004`](../../decisions.md#dec-004), because it needs signal on a run, and because a round trip puts the answer far outside the spoken-response feel the rest of the product has.
- **A fixed command list.** The smallest thing that works, and the `Customer` ruled it out as the whole answer in [`DEC-016`](../../decisions.md#dec-016); a runner who asks in the wrong words gets nothing.
- **An on-device model for intent, with keyword matching behind it.**

## Decision Outcome

An on-device model for intent, with keyword matching behind it. Intent recognition stays on the phone and behind one seam, so the matcher can be replaced without touching the rest of the session.

Keyword matching is what ships today: it reads the transcribed text for the words that name a stat and answers with the stats it found. It is not the end state, and it is what [`FR-004`](../../functional-requirements/fr/FR-004.md) is measured against until a model is measured on a device. A model, Gemma or another, replaces the matcher behind the same seam once a spike shows it fits, and that replacement is a new record rather than an edit to this one.

It beats the other two because it satisfies the `Customer`'s direction without betting the release on an unmeasured model, and because the fallback is a working product rather than a plan.

## Consequences

A question worded outside the matcher's words gets the off-topic reply of [`FR-005`](../../functional-requirements/fr/FR-005.md) rather than the stat the runner wanted. That is a known cost of the fallback, and it is the gap a model is meant to close.

Holding the seam means the question-answering path cannot assume the matcher's shape, so the code carries an indirection that today has one implementation behind it.

The decision accepts these quality attributes:

- **Operability**, covered by [`QR-03`](../../quality-requirements/qr/QR-03.md): the runner speaks rather than looks, which is what keeps the phone in the pocket.
- **Time behaviour**, covered by [`QR-01`](../../quality-requirements/qr/QR-01.md): matching happens on the device, so an answer does not wait on a network, and a model that cannot hold that bound does not replace the matcher.
