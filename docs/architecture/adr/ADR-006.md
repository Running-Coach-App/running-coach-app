# ADR-006: Record Each Spoken Line On The Device As A Structured Log

- **Status:** Accepted
- **Created:** 2026-11-07
- **Updated:** 2026-11-07
- **Containers:** `coach app`
- **Addresses:** [`FR-014`](../../functional-requirements/fr/FR-014.md), [`QR-01`](../../quality-requirements/qr/QR-01.md), [`QR-04`](../../quality-requirements/qr/QR-04.md)
- **Decision:** [`DEC-028`](../../decisions.md#dec-028)

## Context

[`FR-014`](../../functional-requirements/fr/FR-014.md) requires one structured record for every line that falls due, with the outcome and the delay, so an operator can tell why a run went wrong without reproducing it. [`US-13`](https://github.com/Running-Coach-App/running-coach-app/issues/168) is that need. [`SLI-01`](../../observability.md#sli-01) reads those points.

The product serves no HTTP requests. The unit of work is a spoken line, not a route. The course's default observability backend is a self-hosted service the product would export signals to. The team has no such service, and the product has no `INTERNET` permission.

[`ADR-005`](ADR-005.md) already decided that usage events stay in a JSON Lines file on the phone. This record decides the same question for the per-line quality signal.

## Considered Options

- **A hosted observability backend, such as OpenObserve, that the application exports metrics and logs to over OTLP.** It would give the two environment-scoped dashboards and the staging query the diagnosability test is written against. It loses because the team has no backend, because the product has no network permission, and because a session that cannot reach the campus network would emit nothing.
- **The Android system log only.** The points would already be on the device. It loses because logcat is not retained across sessions, is not exportable as the file [`DEC-028`](../../decisions.md#dec-028) prefers, and mixes the coach's records with everything else on the phone.
- **A structured JSON Lines log in the application's private storage, one object per spoken line.**

## Decision Outcome

A structured JSON Lines log in the application's private storage, one object per spoken line. The `coach app` container writes the record when the line is spoken or abandoned, beside the event file [`ADR-005`](ADR-005.md) names, and nothing is sent on its own.

It beats the other two because the operator can read one session's lines in order from a file the runner exports, which is what [`FR-014`](../../functional-requirements/fr/FR-014.md) asks, and because a dropped line still produces a point rather than a gap, which is what [`SLI-01`](../../observability.md#sli-01) needs.

An observability backend, if the team had one, would still be an external system: the product would only send signals to it and would not need it to run. The team would self-host that backend and would not build it. The team has none, so none appears as a container, and the product works with collection off.

A later choice to export the same points over OTLP is a new record, not an edit to this one.

## Consequences

There is no observability dashboard, no organization, and no query endpoint. The [`SLI-01`](../../observability.md#sli-01) queries run against an exported file loaded as a table. The diagnosability test the course describes against a staging organization cannot run until a backend exists.

The log is per line rather than per session, so it grows faster than the event file. Retention is the last 7 days or the last 50 sessions, whichever is reached first.

The decision accepts these quality attributes:

- **Time behaviour**, covered by [`QR-01`](../../quality-requirements/qr/QR-01.md): [`SLI-01`](../../observability.md#sli-01) is the delay between a line falling due and speech starting, so a late line is a measured point rather than a guess.
- **Fault tolerance**, covered by [`QR-04`](../../quality-requirements/qr/QR-04.md): a lost location fix is a recorded interval rather than a silent failure, once [`SLI-02`](../../observability.md#sli-02) has a source.
