# ADR-005: Record Usage Events On The Device As JSON Lines

- **Status:** Accepted
- **Created:** 2026-11-07
- **Updated:** 2026-11-07
- **Containers:** `coach app`
- **Addresses:** [`FR-013`](../../functional-requirements/fr/FR-013.md), [`QR-02`](../../quality-requirements/qr/QR-02.md)
- **Decision:** [`DEC-028`](../../decisions.md#dec-028)

## Context

[`FR-013`](../../functional-requirements/fr/FR-013.md) requires an event for each step of the core task, with the fields [`docs/analytics.md`](../../analytics.md#the-events) names, and with a session identifier that cannot be reversed to the runner. [`US-12`](https://github.com/Running-Coach-App/running-coach-app/issues/167) is the analyst's need to read those events.

The product has no `INTERNET` permission and no joint database. [`DEC-028`](../../decisions.md#dec-028) keeps finished runs on the device. The course's default analytics backend is a self-hosted service the product would send events to. The team has no such service.

The question is where the events live, not whether they exist. [`ADR-001`](ADR-001.md) already decided the product is one Android application; this record decides the pipeline inside that container.

## Considered Options

- **A hosted analytics backend, such as OpenPanel, that the application sends events to over HTTPS.** It would give the two environment-scoped dashboards the course asks for. It loses because the team has no backend, because the product has no network permission, and because a round trip during a session contradicts [`DEC-004`](../../decisions.md#dec-004).
- **A vendor analytics SDK on the phone, such as the Play Store's own metrics.** Crash and install numbers would arrive without a service the team runs. It loses because the event table is the product's own schema, because those SDKs send personal or device fields the telemetry rules forbid, and because a stranger cannot recompute a metric from them.
- **JSON Lines in the application's private storage, exported when the runner chooses.**

## Decision Outcome

JSON Lines in the application's private storage, exported when the runner chooses. The `coach app` container appends one object per event to a file it owns, and nothing is sent on its own.

It beats the other two because it is the smallest pipeline that satisfies [`FR-013`](../../functional-requirements/fr/FR-013.md) under [`DEC-028`](../../decisions.md#dec-028), and because the records can be checked from a unit test with no phone, which is what [`QR-02`](../../quality-requirements/qr/QR-02.md) asks of the coach's decisions.

An analytics backend, if the team had one, would still be an external system: the product would only send events to it and would not need it to run. The team would self-host that backend and would not build it. The team has none, so none appears as a container, and the product works with collection off.

A later choice to send the same events to a backend is a new record, not an edit to this one.

## Consequences

There is no analytics dashboard and no environment scope. The queries in [`docs/analytics.md`](../../analytics.md) run against an exported file loaded as a table, not against a live backend.

The file has to be bounded, or it grows for as long as the app is installed. Retention is the last 90 days or the last 500 sessions, whichever is reached first.

The decision accepts these quality attributes:

- **Testability**, covered by [`QR-02`](../../quality-requirements/qr/QR-02.md): the engine emits events behind a sink that a unit test can read, so a change that drops a step of the core task fails from a clean checkout.
